# ADR-0068: The dash is the host the keypad never had

**Date:** 2026-09-04
**Status:** Accepted
**Repos:** `RDM-7_Dash` (this one), `rdm7-desktop`
**Related:** ADR-0055 (the dash as CAN gateway), ADR-0058 (render in colour the
hardware does not have) and its sixth addendum, ADR-0059 (the last frame is the
one that stays), ADR-0063 (the lighting the part actually has)

## Context

A Blink keypad cannot animate itself. The only self-driven show it has is the
factory one in CANopen object `2014h` — three fixed choices, none of them
yours. Everything else is fed to it frame by frame by a host.

RDM Studio became that host (ADR-0058): it designs a boot, bakes it to timed
CAN frames, and streams them through the dash's `/api/can/send` gateway one
frame per HTTP round trip. That works, and it is a bench feature. The boot
people actually want is the one that plays when they turn the key, in a car
with no laptop in it, and the honest line in the docs said so:

> **The dash does not play boots yet.** Today a boot needs Studio open.

Three things made that gap closable rather than a rewrite:

- the dash is already on the bus, already transmits, and is powered by the
  same ignition as the keypad;
- Studio already bakes the boot to a frame list, because the "Frames" export
  writes exactly that for USB-CAN tools;
- ADR-0059 already forced the file to say what its tail MEANS — whether the
  last frame holds or the tail loops — which is the only thing a dumb player
  cannot work out for itself.

## Decision

**The dash plays the tape. It does not own the show.**

`main/can/keypad_lights.c` is a tape player: it stores one baked file on
LittleFS, and at power-up it NMT-starts the node, waits for the keypad's own
start-up show to get out of the way, and transmits the frames on their own
clock. Two endpoints (`GET`/`POST /api/keypad/lights`) store it, report it,
and can replay or forget it.

There is no effect engine here, no button state machine, no channel bindings —
that is the keypad manager from the platform plan, and it is a different piece
of work. Everything clever stays in Studio, where you can see it while you make
it. The dash is told *what frames, when*, and nothing else.

Three refusals are the design:

- **It will not play on the wrong bitrate.** The setup wizard is allowed to hop
  the dash's rate because a human is watching a bench (ADR-0055). A boot player
  runs at ignition in a moving car; re-timing the bus there to light some LEDs
  is not a trade anybody would take. Mismatch → it says so and does nothing.
- **It will not play while the bus scan owns the peripheral.** Same reason the
  gateway refuses: a transmit would fail as `INVALID_STATE` and read as a dead
  keypad.
- **It is rate-capped like `/api/can/send`.** Studio's baker already keeps every
  boot inside the dash's 24-frames-a-second budget, but the file arrives over
  the network and "Studio would never send that" is a hope, not a guarantee.

**The tail contract carries across the repo boundary unchanged.** `loop: false`
means the last frame is the hand-back — every ring the buttons are not lighting,
dark — and the player stops transmitting after it, leaving the rings to whatever
normally drives them (usually the ECU). Silence is the point. `loop: true` means
the frames from `loop_from_ms` are one turn of a resting animation and get
repeated, because replaying an animation once and stopping leaves the keypad
frozen on whichever frame it ended on.

**A bad upload never replaces a working boot.** `keypad_lights_store()`
validates into memory first and only then writes, with the same
tmp + fsync + rename idiom as `channels.json`.

## Consequences

The Lights page in Studio gains one button — *Put it on the dash* — and the
line that used to say "needs Studio open, with a dash on WiFi" now says "on the
dash — it plays at every power-up, with Studio shut". Studio checks the two
limits the C player has (384 frames, 60 s) BEFORE sending, because the player's
only other option is to truncate, and half a boot is worse than none.

The file crosses a repo boundary, so it is tested from both ends. Studio's
harness asserts the shape it emits; `tests/native/test_keypad_lights.c` parses
the bytes it actually emitted, from a fixture generated by:

```
node tools/check_lightshow.js --emit-tape \
     ../RDM-7_Dash/tests/native/fixtures/keypad/boot_tape.json
```

Regenerating that fixture is how you find out a change to the baker broke the
player. Ten native tests cover the parse, the refusals, the bounds and the tail.

What is still Studio's alone: the *reaction* to a key press. The dash would have
to read the keypad's key frame and re-render the resting look over it, which is
the LED engine, which is the keypad manager. Studio can now watch real presses
through the gateway and preview them (ADR-0058's sixth addendum); the car
cannot play them yet, and the page says so.
