# Firmware quirks — where the device JSON differs from the catalog

The catalog (02) is generated from the **editor's** schema. A handful of fields
are converted by the editor before saving, or are derived from somewhere else
entirely, so the *device JSON* you author here wants different fields than the
catalog shows.

The catalog flags every one of them with **X** and repeats the list in each
widget's header — that flagging is generated by diffing the schema against each
`widget_<type>.c`, so it can't go stale. This page says what to write instead.

**The current set of schema fields that are NOT `config` keys:**

| widget | field | what to write / where it really comes from |
|---|---|---|
| `meter` | `start_angle_user`, `sweep_degrees` | `start_angle` + `end_angle` (LVGL) — see below |
| `meter` | `minor_tick_step`, `major_tick_step` | `minor_tick_count` + `major_tick_every` — see below |
| `arc` | `start_angle_user`, `sweep_degrees` | `start_angle` + `end_angle` (LVGL) — see below |
| `arc` | `arc_low`, `arc_high` | the **bound channel's** low/high thresholds |
| `bar` | `bar_alerts_enabled` | derived: alerts are on when the channel's thresholds differ from its range |
| `warning` | `lamp_on` | rule-only — a rule override target, never a `config` key (see 06) |
| `anim` | `anim_upload` | an editor upload button, not data |

---

## 1. Dial angles are LVGL angles ⚠️

`meter` and `arc` store **`start_angle` and `end_angle`**, both in **LVGL**
convention: **0° = 3 o'clock**, increasing clockwise. The editor shows you
`start_angle_user` (0° = **12 o'clock**) and `sweep_degrees`, and converts.

```
lvgl_start = (user_start + 270) % 360
lvgl_end   = (lvgl_start + sweep) % 360

user_start = (lvgl_start + 90) % 360
sweep      = (lvgl_end - lvgl_start + 360) % 360
```

The default dial — user start 225°, sweep 270° (starts lower-left, ends
lower-right) — is `"start_angle": 135, "end_angle": 45` in device JSON.

**Full circle:** a 360° sweep means `start_angle == end_angle`. Don't write a
sweep of 0 expecting a full circle from some other field, and don't write
`end_angle = start_angle + 360` — it wraps to a 0° dial.

Setting `start_angle_user`/`sweep_degrees` in device JSON does nothing at all —
the dial silently keeps its defaults. This is the single most common way to get
a gauge pointing the wrong way.

## 2. Meter ticks are COUNT-based, not step-based ⚠️

For a `meter`, the device JSON uses:

- `minor_tick_count` — **total** minor ticks across the whole min..max range
  (a `uint8_t`, clamped to 2..255).
- `major_tick_every` — every Nth minor tick is promoted to a major tick.

Convert "ticks every S units, majors every M units" over range `min..max`:

```
minor_tick_count = round((max - min) / S) + 1
major_tick_every = round(M / S)
```

Example — a 0–8000 tach, minor every 250, major every 1000:
`minor_tick_count = 8000/250 + 1 = 33`, `major_tick_every = 1000/250 = 4`.

The **medium** tier is the exception: `mid_tick_step` IS in display units (set
`0` to disable). `tick_label_divisor` is used directly (e.g. `1000` shows a 7000
tick as "7").

`arc` and `pathbar` are **step-based** (use `minor_tick_step` / `major_tick_step`
as the catalog shows) — no conversion needed. Only `meter` deviates.

## 3. Alert points come from the channel, not the layout

`arc_low`/`arc_high` and `bar_alerts_enabled` are read from the **bound
channel's** thresholds. `redline_enabled`/`redline_threshold` *are* real config
fields, but a channel carrying a high threshold turns the zone on by itself and
its value wins. To move where a gauge goes red, edit the channel
(`/api/channels/update`), not the layout. See 04.

## Other notes

- Config key is `signal_name`, not `signal`.
- **Colours are RGB565 integers, never `"#RRGGBB"` strings.** The firmware tests
  `cJSON_IsNumber()` and silently ignores anything else. See 03.
- A meter is kept square by the firmware; set `w == h`.
- Per-type `w`/`h` limits (catalog index table) are the **editor's** resize
  limits, not a runtime clamp. `widget_constraints[]` exists in
  `widget_types.c` but nothing in the firmware reads it — the device draws
  whatever size you give it. Small text widgets in real layouts sit well under
  the stated minimum. The catch is the editor: it snaps a widget to these
  limits as soon as someone drags it, so a layout built outside them changes
  shape the first time it's edited by hand.
- **`bar` draws a label above itself and falls back to the literal `"BAR1"` /
  `"BAR2"` when `config.label` is empty.** To hide it, set
  `"show_bar_label": false` — that's the field for it. (Older layouts used a
  single-space `label` as a workaround; still works, but `show_bar_label` is the
  right answer now.)
- `track_map` has **no night-mode support in firmware** even though the schema
  marks its colours night-overridable. `config.night` on a `track_map` is
  ignored. Every other widget except `pathbar` honours it.
- `pathbar` and `anim` do **not** support conditional rules (see 06).
- **Custom "legit" ticks via per-tick IMAGES (arc + meter).** Drawn rectangle
  ticks look basic; for tapered/glowing/neon ticks (e.g. a McLaren rev ring) set
  `major_tick_image_name` / `mid_tick_image_name` / `minor_tick_image_name` to a
  small uploaded image and size it with `*_tick_image_scale` (percent; 100 =
  native px). The firmware stamps + **rotates** the image to each tick's radial
  angle and bakes it into the static-tick snapshot → **free at runtime**. This
  is the one image exception that doesn't violate the procedural rule (tiny,
  baked, dynamic-safe). Per-tier extras: `*_tick_image_offset` / `_opa` /
  `_recolor` / `_recolor_opa`. Pipeline in 07-assets-and-tracks.

## Design philosophy: PROCEDURAL, not images — big images aren't for pro layouts

Professional layouts are built from **drawn widgets** — needles, ticks, arcs,
bars, text, shapes — **not baked raster images**. Images don't scale: they eat
flash + LittleFS, hit a *contiguous*-PSRAM decode wall (largest free block is
often <0.5 MB once a layout loads → the image silently fails to paint and the
widget shows its *name* as fallback), can't recolour/restyle live, and look
dated. Build the gauges; reach for an image only for tiny icons.

**Hard rules (default to ALL of these):**
- **NO full-screen (800×480) background image** (~1.15 MB). Use a full-screen
  **`shape_panel`** (a drawn rect, ~zero cost) + `line`/`text`/`arc`/`meter`.
- **NO meter/arc "dial face" background image, NO image-fill gauge, NO image
  needle, NO image ticks** in a normal layout. These were stepping stones — the
  drawn equivalents below now look as good and stay dynamic (recolour, night
  mode, live values).
- **Images ONLY for small icons** (≤~40 px): a logo, telltale glyphs (turn
  signals, high-beam, oil, battery, temp). Decoration, never a gauge surface.
- **All-widget dashes apply with a plain `save`+`set`** (no reboot, no PSRAM
  wall). Bind every readout to a real channel via a `panel` (`show_unit` pulls
  the channel's unit + decimals).

**Build premium gauges procedurally:**
- **Round gauge** = `meter` (needle) or `arc` (sweep fill). Both draw ticks +
  numbers themselves.
- **NEEDLE** = `meter` drawn needle with a **tip style** (Dagger / Spade /
  Diamond — see the meter's needle fields in `02-widget-catalog.md`) + a centre
  ball, and now a **drawn drop shadow**: `shadow_enabled` +
  `shadow_offset_x/_y` + `shadow_opa` + `shadow_width_extra` (spread into a soft
  penumbra) + `shadow_dynamic` (swings with the needle, as if lit from above).
  Tapered tip + ball + shadow reads far better than a flat line, and it all
  recolours live. (Never a baked image needle.)
- **TICKS** = `show_ticks` + per-tier length / width / colour
  (`{major,mid,minor}_tick_length` / `_width` / `_color`). For the raised /
  embossed **"pop"** that used to need a baked image, use the drawn **tick
  outline/glow** (arc + meter): `tick_outline_strength` (0-255) +
  `tick_outline_color` (usually black) + `tick_outline_fade` (0 = hard edge,
  higher = soft glow). It bakes into the static-tick snapshot → **free at
  runtime**.
- **FILL / glow** = `arc` (or `bar`, or `rpm_bar`) value fill with a multi-stop
  **`grad_stops`** gradient (up to 8 stops — see 03) plus a `lead_edge_enabled`
  glowing tip. A drawn gradient fill with a bright lead-edge reads premium
  without a baked tube. (`grad_enabled` + `grad_end_color` is the legacy 2-stop
  form; it still loads but writes back as `grad_stops`.)
- **CURVES** — a `line` now takes a `curvature` (bend it into an arc), and
  `pathbar` bends the whole bar along a path with `label_side` /
  `label_every` / `label_along_offset` to keep its numbers readable.
- A true soft *bloom* is the only thing widgets can't draw — and a pro layout
  doesn't need one. The lead-edge + tick outline give all the "pop" required.

## Golden rule: copy a working widget

The surest way to get a widget's exact, current device fields is to **adapt a
real one** rather than author from memory:

- `GET /api/layout/current` on a live device — the exact JSON the firmware is
  rendering right now. **Best source, always.**
- `examples/ford_cluster.json` — a real 35-widget cluster (`pathbar`, `meter`,
  `arc`, `bar`, `text`, `line`, small `image` icons).
- `examples/feature_demo.json` — smaller, but exercises `grad_stops`, `rules`,
  `night`, needle shadow, tick outline and a converted dial angle.

Then trim to defaults-only and run `validate_layout.py`.
