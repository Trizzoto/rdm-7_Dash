Clean `idf.py build`, flashed to COM27, hardware boot confirmed clean (`lifetime panic_count=0`, `TWAI state=RUNNING`, 141/160 URI handlers, WiFi connecting) — no crash/panic/watchdog. **One real gap surfaced but deliberately NOT fixed this pass** (documented in a code comment at `_sim_inject_clear_ack`): a real ECU's strict 1-byte Mode 04 clear-DTC ack (SF PCI declaring length=1, just the `0x44` echo) would be silently dropped by `obd2_rx_handler`'s `len_bytes < 2` guard before it ever reaches `_process_full_message` (which has its own, redundant `len < 2` guard too) — meaning a real "clear DTCs" call against such an ECU would currently fall through to the timeout path instead of firing its callback promptly. - **Two real bugs in `main/can/obd2.c` found and fixed while hand-tracing the mirror against the real code** (not hypothetical — reproduced by 3 failing tests before the fix): (1) the VIN/ECU-name leading-padding strip used a NUL-terminated `char *start; while (*start && ...) start++;` pointer walk — since `*start == 0x00` is falsy, this loop guard treats a raw NUL pad byte as end-of-string and stops *before* skipping it, so despite the code comment claiming "some ECUs pre-pad with NULs, strip them," a NUL-padded response came out as an **empty string**, not a stripped one. (2) even with the strip logic bounded by index instead of NUL-termination, it still ran *after* the fixed-size take-window (17 bytes for VIN) was already copied, so N bytes of leading padding silently truncated the *last* N characters of the real VIN/name. Fixed both by moving the leading-non-printable strip to run on the raw `p`/`plen` *before* computing `take`, in both the VIN and ECU-name branches. Small, isolated to post-copy buffer cleanup (no state-machine/arm/timeout/control-flow changes). Real-world severity is likely low (the SAE-standard DI-byte prefix, 0x01-0x05 with a matching length, was already handled correctly before this fix; this only affected non-standard NUL-padding some ECUs might add) but it's a genuine correctness bug either way. **Verified**: full native suite (11 binaries, 196 tests, 0 failures via `run.ps1`), clean `idf.py build` (only `obd2.c.obj` recompiled), flashed to COM27, hardware boot confirmed clean (`lifetime panic_count=0`, `TWAI state=RUNNING`, web server 141/160 handlers registered, layout loaded, WiFi connecting) — no crash/panic/watchdog.

## Notes for whoever picks this up

- Build: `. "$env:IDF_PATH\export.ps1" *> $null; idf.py build` (PowerShell). Flash: `idf.py -p COM27 flash` (port can renumber — check `[System.IO.Ports.SerialPort]::GetPortNames()` first).

Don't mistake "boots clean" for "serial protocol verified" until that flag is off or a build without it is tested.
- Native test suite: `tests/native/run.ps1` (Windows-friendly, no `make` needed here). `tests/native/Makefile` also works if `make` is ever available.
- The dash is reachable over WiFi at `http://192.168.4.63` (confirmed working this session, `GET /api/selftest` responds; IP is DHCP-assigned and can change — rediscover via a subnet sweep hitting `/api/selftest` if it moves). `GET /api/screenshot` returns a JPEG — useful for visual before/after diffing of rendering changes without needing computer-use or physical access to the touchscreen (used this session to confirm the gauge-tick refactor was byte-identical pixel-for-pixel).
